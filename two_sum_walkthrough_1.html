Two Sum, 긴 예제로 손으로 따라가기

이중 반복문 없이 딕셔너리 하나로 두 수의 합 문제를 O(n)에 푸는 코드를, 조금 더 긴 예제로 한 줄씩 직접 따라가며 이해합니다.

01코드

def two_sum_fast(nums, target): seen = {} # 값 -> 인덱스 for i, num in enumerate(nums): complement = target - num if complement in seen: return [seen[complement], i] seen[num] = i return None

핵심 아이디어: "지금까지 봤던 숫자들"을 딕셔너리에 저장해두고, 매번 "target을 만들려면 필요한 나머지 숫자(complement)"가 이미 나온 적 있는지 확인합니다.

02예제 설정

nums = [4, 8, 15, 3, 7, 2] target = 10

이 리스트를 처음부터 끝까지, seen 딕셔너리가 어떻게 채워지는지 함께 따라가 보겠습니다. 시작할 때 seen = {} (빈 딕셔너리)입니다.

여기서 함수가 끝납니다. i=5(num=2)는 확인할 필요조차 없었습니다.

05여기서 눈여겨볼 점

  • 한 번도 뒤로 돌아가서 다시 훑지 않았습니다. 매 순간 "지금까지 본 값들"만 seen에 쌓아뒀다가, 필요한 순간(complement in seen)에 O(1)로 바로 찾았습니다.
  • 이게 바로 O(n²) → O(n)으로 줄어드는 이유의 출발점입니다. 정확히 왜 그런지는 아래에서 이중 반복문과 나란히 비교하며 확인합니다.

06이중 반복문은 실제로 어떻게 동작하나

정정. 이중 반복문이 "이미 본 값을 또 확인하는 중복 작업"을 한다는 설명은 정확하지 않습니다. 실제로는 같은 쌍(pair)을 두 번 비교하지 않습니다. 진짜 문제는 다른 데 있습니다 — 아래에서 직접 추적해봅니다.
def two_sum_brute(nums, target): n = len(nums) for i in range(n): for j in range(i + 1, n): if nums[i] + nums[j] == target: return [i, j] return None

같은 예제 nums = [4, 8, 15, 3, 7, 2], target = 10 으로 직접 추적하면:

흥미로운 점. 이중 반복문은 9번 비교 후 [1, 5] (8과 2)를 찾았는데, 딕셔너리 버전은 [3, 4] (3과 7)를 찾았습니다. 둘 다 유효한 정답이지만, 탐색 순서가 다르면 반환되는 정답도 달라질 수 있습니다.

같은 형식으로 각 i가 몇 번 비교하는지 정리하면:

  • i=4 고정 → (4,8)(4,15)(4,3)(4,7)(4,2) → 5번 비교
  • i=8 고정 → (8,15)(8,3)(8,7)(8,2) → 4번 비교
  • i=15 고정 → (15,3)(15,7)(15,2) → 3번 비교
  • i=3 고정 → (3,7)(3,2) → 2번 비교
  • i=7 고정 → (7,2) → 1번 비교
  • i=2 고정 → 더 이상 오른쪽에 남은 값 없음 → 0번

같은 쌍을 두 번 비교하는 중복은 없습니다. (4,8)을 i=4일 때 확인했으니 i=8일 때 (8,4)를 다시 확인하지 않는 이유는, j가 항상 i보다 오른쪽부터 시작하기 때문입니다(range(i+1, n)). 진짜 문제는 "중복"이 아니라, 확인해야 하는 쌍의 총 개수 자체가 n이 커질수록 매우 빠르게 늘어난다는 것입니다.

07왜 이중 for문이 O(n²)인가

총 비교 횟수 = 5+4+3+2+1+0 = 15번 — 바로 위에서 직접 추적했을 때 9번 만에 찾았지만, 정답이 없거나 맨 끝에 있었다면 최대 15번까지 확인해야 했을 것입니다.

일반화 (n이 임의의 수일 때)

총 비교 횟수 = (n-1) + (n-2) + (n-3) + ... + 2 + 1 + 0

이건 1부터 n-1까지 더한 것과 똑같은 모양입니다 — 자료 초반 실습의 "1부터 n까지의 합"과 정확히 같은 구조입니다. 그 공식을 그대로 쓰면:

총 비교 횟수 = n(n-1) / 2

왜 "O(n²)"으로 표현되는지

n(n-1)/2 = (n² - n) / 2 = n²/2 - n/2

빅오 표기법의 규칙을 그대로 적용합니다: 계수(1/2)는 생략, 최고차항이 아닌 항(−n/2)은 생략 → 결과: O(n²)

08저장만 해두면 빨라질까? — 리스트 vs 딕셔너리

여기서 자연스러운 의문이 생깁니다: "본 값들을 저장해두는 것" 자체가 핵심 아닌가? 저장하는 개수는 브루트포스가 확인하는 개수와 다르지 않은데, 뭐가 다른 걸까요?

답은 "저장 여부"가 아니라 "저장해둔 곳에서 찾는 방법"에 있습니다. 만약 딕셔너리 대신 리스트에 저장했다면 어떻게 될까요?

def two_sum_list_version(nums, target): seen = [] # 리스트에 저장 for i, num in enumerate(nums): complement = target - num if complement in seen: # 리스트에서 찾기 j = seen.index(complement) return [j, i] seen.append(num) return None
이 버전은 사실 O(n²)입니다! 리스트에서 complement in seen을 확인하려면 seen 안의 값을 하나씩 다 비교해봐야 합니다. 저장된 값이 6개면 최대 6번, 100개면 최대 100번 — 결국 앞서 세었던 "5+4+3+2+1+0"과 똑같은 총 비교 횟수가 나옵니다.

그럼 딕셔너리는 왜 다른가

딕셔너리(해시 테이블)는 "하나씩 비교하며 찾기"를 하지 않습니다:

seen[8] = 1 이라고 저장할 때 → 8이라는 값을 해시 함수에 넣어서 "저장할 위치"를 바로 계산합니다. → 예: hash(8) → "이 값은 105번 칸에 넣어라" 나중에 8이 seen에 있는지 찾을 때 → 8을 또 해시 함수에 넣어서 "105번 칸을 확인하면 되겠구나" 하고 바로 직행합니다. → 앞에 저장된 4, 15, 3 ... 을 하나씩 비교할 필요가 전혀 없음

그래서 딕셔너리에 몇 개가 저장돼 있든(10개든 100만 개든) in 연산은 거의 항상 한 번의 계산으로 끝납니다. 이게 O(1)이라는 뜻입니다.

방법저장 방식"있나?" 확인 방법확인 1번당 시간총 시간
이중 반복문저장 안 함매번 남은 원소 다 비교—O(n²)
리스트에 저장리스트리스트 안을 하나씩 스캔O(n)O(n²) (동일!)
딕셔너리에 저장해시 테이블해시로 위치 바로 계산O(1)O(n)
결론. "저장해두느냐 마느냐"가 아니라, 저장은 하되 찾을 때 하나씩 비교하지 않고 한 번에 찾을 수 있는 구조(해시)를 쓰느냐가 O(n²)와 O(n)을 가르는 진짜 이유입니다.

09두 방식, i별로 나란히 비교

딕셔너리 버전도 브루트포스와 같은 형식으로 풀어서 적어보면, 왜 다른지가 더 명확해집니다.

i=4 (num=4) → complement=6, seen={} 에 있나? → 없음 → seen[4]=0 저장 (확인 1번) i=8 (num=8) → complement=2, seen={4} 에 있나? → 없음 → seen[8]=1 저장 (확인 1번) i=15(num=15) → complement=-5, seen={4,8} 에 있나? → 없음 → seen[15]=2 저장 (확인 1번) i=3 (num=3) → complement=7, seen={4,8,15} 에 있나? → 없음 → seen[3]=3 저장 (확인 1번) i=7 (num=7) → complement=3, seen={4,8,15,3} 에 있나? → 있음! → [3, 4] 반환 (확인 1번)
i=4일 때i=8일 때i=15일 때i=3일 때
브루트포스(4,8)(4,15)(4,3)(4,7)(4,2) → 5번 비교(8,15)(8,3)(8,7)(8,2) → 4번 비교(15,3)(15,7)(15,2) → 3번 비교(3,7)(3,2) → 2번 비교
딕셔너리complement=6 확인 → 1번complement=2 확인 → 1번complement=-5 확인 → 1번complement=7 확인 → 1번
핵심 차이. 브루트포스는 i가 고정될 때마다 오른쪽에 남은 값들과 하나하나 비교합니다(5,4,3,2,1번으로 점점 줄지만 매번 여러 번). 딕셔너리는 i가 바뀔 때마다 "이 값이 있나?"를 항상 딱 1번만 확인합니다. "i를 고정하고 오른쪽 값들을 훑는" 과정 자체가 딕셔너리 버전에는 존재하지 않습니다. 매 원소마다 저장된 곳에 이 하나의 값이 있는지만 즉시 확인하고 끝나는 구조라서, 원소가 몇 개든 각 단계는 항상 O(1)로 끝나고, 전체는 O(n)이 됩니다.
